# 真实用户问答测试与升级策略（2026-10-10）

## 测试口径

本轮在本地 Docker 运行真实 Agent 聊天请求，不修改生产服务。起始代码 `96ff32303151a06ea9d6d7d98acfb34596ee8a7b`。测试账户使用现有“表格数据分析（结构化）”Agent；实际回答记录的模型为 `qwen-max`，字段识别模型也为 `qwen-max`，字段服务版本 `semantic-fields-v22.2-compound-statistics`。页面输入区当前显示的模型不作为已执行请求的模型证据。

数据集为 `424aed70d6a68ef7b97a067e`，669 个已导入系列。原文件 SHA-256：`108b08e3f40b1f2cb081ca406fdc4bd02415dce5ffd2c7426d078c79573bd1fe`。原始 Excel 只读核对采用独立的 openpyxl/numpy 脚本，不从被测查询服务生成正确答案，不重算或修改 Excel。

52 个问题包括：别称、省略年月/主语、普通文字确认、纠正口径/切换合约、目录查询、点值运算、百分比、跨日比较、窗口统计、Top N、过滤后极值、条件计数、跨表价差、年度标签、累计量的业务含义、相关性、回撤、预测、因果证据、缺数、非法日期、公式零缓存、画图。问题通常不指定工作表；明确合约的对照组用于区分“确有字段歧义”和“计算能力缺失”。

会话内依序发问，会话间隔离。真实聊天保留 SSE、工具入参/输出、最终文本、持久化消息与耗时；另外对 U11/U12/U13 直接调用字段层进行定位。直接字段层成功不算聊天测试通过。网页抽查单独注明；其余案例依据 API 记录及对应渲染逻辑核对，不宣称逐一点击了 52 次网页。

评分区分：完整正确、合理澄清、部分正确、失败。未知合约/不同库存口径确实影响答案时，允许询问。不能把参数错误、执行器不支持或模型生成方案不完整说成用户字段不清楚。`complete`、工具 `success=true` 和 `resolved` 都不等于业务正确。

## 已确认的主要问题

### P0：查询范围和条件丢失后仍输出成功结果

| 案例 | 实际行为 | 原表核对 / 正确行为 |
|---|---|---|
| U44 最近 5 个交易日均值并列出 5 天 | `mean` 无时间边界，统计全部 4701 条，得到 15889.0417；最终文本还编出 5 天价格 | 2023-09-18 至 09-22，B4701:B4705，均值 **17190**；对应值 17195、17370、17165、17110、17110 |
| U48 2023 年 9 月均值 | 同样算全部历史，15889.0417 | 9 月 16 条有效记录，均值 **17280.625** |
| U46 排除 0 和空值后的最低价 | 工具仍返回 0（B4484）；文本另说 13630（2004-06-03），两者都不满足要求 | 正数最低值 **9990，2016-02-29，B2860/A2860** |
| U47 2023 年超过 17000 的交易日数 | 年范围正确，阈值丢失，统计全部 178 个有效交易日 | 满足条件的为 **47 天** |
| U45 最高的三天 | `max` 只返回最高的一天，并称只有这一天是最高 | Top 3 为 34245（2011-02-17/B1638）、33910（02-16/B1637）、33795（02-11/B1634） |
| U30 11 月累计入库量按日加总及重复计数解释 | 范围丢失，全部历史加总 19897184.6875；文本解释累计量重复计数，普通源卡片却隐藏了这一解释 | 11 月有效观测的算术和为 **15237195.5779**；这仍是累计值之和，不是当月入库流量，应明确缺数与重复计数 |

当前 query 合约只允许 rows/latest/max/min/mean/sum/count/statistics、日期范围和 period；没有 value filter、order/take、交易日窗口。模型输出没有这些字段时仍能通过校验，执行器因此悄悄把复杂问题降成简单统计。部分月/年问题又被 Agent 填入不合法的 `date=2023-09` 或 `2023`，要求用户重新给某一天。

**策略：先检查任务覆盖，再执行。** 把本轮需求拆成可核验的目标：字段、范围、阈值、排序/条数、统计、输出明细。执行前逐项核对方案；不支持时返回 `unsupported_task`，不能执行一个不等价的替代查询。新增受限、带类型的 filter/order/take/window 运算后，程序根据原表记录排序选取窗口，再计算。交易日数依据原表观察日期，不用日历天数替代。统计样例行不能当全部输入，更不能被模型编成最近 5 天。

### P0：绕过原表回答，或把系统错误说成没有数据

U11“郑棉期货有几种价格？就告诉我种类和区别”没有任何工具调用，模型按常识说开盘、收盘、最高、最低、结算、最新共 6 种。原表表头只有收盘、结算两种。直接字段层相同原话返回 count=2，可定位为 Agent 路由/回答约束失效。

U12 库存目录问题的字段模型方案校验失败，外层却说“没有找到库存数据”，并让用户确认上传或表名；U22 开机率别称出现候选 ID 校验错误，同样被说成缺数据。文件里实际存在库存天数、在库量、纯棉纱负荷等字段。U12 字段层重试可以返回目录，但把抛储上市/成交等流量也混入库存类别，分类质量仍需改进；一次重试成功不能覆盖原聊天失败。

**策略：用状态区分事实与故障。** `no_data` 必须来自已经完成的实际查询；`system_error`、`invalid_plan`、`unsupported_task`、`needs_clarification` 独立处理。表格 Agent 回答文件目录、数据或统计前应有有效工具证据；无证据的“种类数”“没有数据”等不能完成为事实答案。分类优先引用真实字段 ID，再由程序回填表名/指标，避免让模型重新拼写大量表头。说明“价格的概念区别”可作为解释，但不能冒充文件中存在的字段。

### P1：连续追问的事实状态仍依赖模型转述

U03“新疆棉2022/11/20当天进仓多少”正确查到 45662.6916（E55/A55）。U04“21号呢？”的 Agent 入参包含可靠日期 2022-11-21，却遗漏 `prior_series_ids/context_sheet`，还填了 schema 中没有的 role；字段层随后询问国产/印度/越南“21号纱线价格”。这不是用户有歧义。

U09“就要收盘价，主力那个”已确认 CF.CZC；U10“那一天结算比收盘高多少”仍要求选合约。U41/U42 明确 CF.CZC 后查询及复合极值成功，U43 仅切换为同一天结算和收盘两个原值，又要求重新选合约。实际传入了 prior close ID，但模型没有稳定继承它的合约维度。

**策略：保留原话，另传结构化会话状态。** 程序从已经成功的工具结果维护 dataset、真实 series ID、商品/合约维度、指标口径、点值日期、统计范围、待确认事项。主语省略时继承商品/合约；“21号”“那一天”按明确时间指代补时间；“最高/最低”未限定范围时重置为全历史；显式换主题/合约/口径时只更新相关槽位。不要简单把整段历史拼进问题，也不要为了保留原话而丢掉可靠状态。新问结算价时可按已经确认的合约维度寻找对应结算系列，不应把所有合约重开一遍。

### P1：单日四则运算被拒绝，复杂计算缺少多阶段表示

U13 结算减收盘、U14 以收盘为分母的百分比、U16 累计公检量除累计入库量都报“多阶段统计与换算尚不能合并执行”。字段层 U13 重现：模型已经提出 `v1-v2`，但同时把单日填入 `query.start_date/end_date`；`validate()` 将有 bounds 的 calculation 全部拒绝，连两界相等的单日也拒绝。模型还会把“主力”扩成多个合约，以及为未知单位提出元/吨。

**策略：规范化单日与范围表示。** 两界相等的单日查询统一成点值计划；合法的点值加减、比例由程序计算，程序判断单位兼容性。跨日变化需要两个独立日期绑定；多个输出应允许表达式列表，不能因“差多少、涨幅多少”两个结果而要求重新选字段。随后升级为受控计算图：源字段 → 日期/条件过滤 → 按日期对齐 → 聚合 → 四则/分析 → 结果。相关系数/回撤等由确定性代码执行，不让模型心算。

### P1：字段候选缺少来源质量和时效信息

U24“最近3128棉花现货一吨多少钱”选择了日报的 6 行小表，给 2023-07-21/J11 的 18035。另有 TTEB价格及进口棉人民币表中 2023-09-21 的有效 18195，且明确单位元/吨。日报原表单位未知，最终文本自行补了元/吨。小表原值是真实的，问题在于未解释为何将更旧、无单位的来源作为总体最新现货报价。不同口径不应仅凭日期合并；应显示差异并择定可信口径。

当前发给字段模型的精简目录保留 metric、unit、dimensions 等，却省略日期覆盖、有效记录数量和来源质量；检索以中文字双字片段 BM25 为主，候选上限 64。别称匹配与小表的字面“现货”可能挤掉更新、更完整的系列。

**策略：改成分层、混合召回。** 将商品/主题、指标定义、合约/规格、单位、来源、时间覆盖分开检索；准确表头与已确认 ID 优先保留，BM25 与字段元数据语义检索合并；对多输入任务逐项召回，避免一类同名价格占满候选。别称来自真实表头、描述、审核后的映射和用户确认积累，绑定实际 ID，不做一套棉花专用猜词规则。比较实际定义一致性后再使用完整性、最新有效日期与明确单位排序；定义确实不同才澄清。

### P1：年度图表规则错误地裁剪了跨表查询目录

U50 明确问“2023年郑棉 CF.CZC 收盘价和纯棉纱负荷相关吗”，返回郑棉字段没有候选、负荷只剩一条 2023 图表曲线，并要求用户提供已经明确的郑棉字段。记录中的 `catalog_count=1`、`full_catalogue_checked=true` 不能理解成检查了原来的 669 个字段。

不调用模型的对照已复现：原话目录只有 1 条，CF.CZC 被排除；去掉“2023年”，或者把它写成完整日期范围“2023年1月1日至2023年12月31日”，目录恢复 669 条，CF.CZC 存在。代码 `native_charts.catalog()` 把年份匹配到年度图例，再结合“纯棉纱负荷”标题匹配，误判图表请求并只保留图表视图。这是可确认的启发式规则缺陷。

**策略：图表引用与查询范围分离。** 只有用户明确要求某张图/某条曲线时，才收窄为图表数据；普通年份和真实字段名不能隐式限制来源。跨表计算所需原表字段必须保留，图表视图作为补充候选；`full_catalogue_checked` 应说明实际检查的文件、表、字段数与原始总数。恢复召回后仍需新增日期对齐和相关执行器。本轮独立原表对照：2023 年两列共同有效日期 36 个，Pearson 系数约 **0.12159005**；这是描述性相关，不是因果证明。

### P1/P2：文本与卡片不是同一个事实输出

U07 工具与卡片保持单位未知，模型文本却补元/吨；U44 编造五个日值；U46 工具卡片给 0，文本给 13630。当前卡片抑制部分文本降低了网页暴露，但 API、导出或其他客户端仍会收到错误文本。不能把隐藏文本当作模型已正确。

**策略：统一一个经过验证的最终答案对象。** 数字、单位、日期、出处均从同一计算结果回填；模型只能写有证据绑定的解释，新增数字须核验。完成事件的状态应同时覆盖任务完成度、数据质量、计算和解释。前端按 turn/request ID 绑定最终对象，只展示本轮已完成答案；若只有部分子任务成功，明确标明未完成项，并保留解释，不把成功的一个数包装成完整分析。浮点数展示按精度格式化，原值和计算精度保留。

U51 没有编造未来价格，文本也指出最后记录为 2023-09-22，但实际计划是查 2026-10-11 的点值；网页普通卡片隐藏了预测边界说明。U40 画图请求因月份被当成不合法单日而失败，没有生成图。页面回放抽查验证了库存追问、复合极值零缓存提示和错误统计最终态；未做高频实时截图/断网恢复测试，因此本轮不能证明所有闪烁或跨轮串答案问题已消失。

## 提示词与上下文拼接建议

1. 统一 Agent 注册提示词、运行时规则和字段提示词中的协议，避免三处长规则互相竞争。保留少量关键约束：原话、独立结构化状态、真正歧义才问、系统错误不可转成缺数、未覆盖任务不得完成。
2. 提示模型先输出任务清单及所需输入，再选列和生成计划。示例包括窗口、过滤、Top N、多个结果、跨日与跨表，不只覆盖最高/最低差值一种模式。
3. 传递“原始用户问题 + 已验证状态 + 当前任务需求 + 候选字段及证据”，不拼接历史猜测、失败参数、上轮答案数值或多轮长推理。前一问题日期只在指代关系明确时继承。
4. 字段候选用稳定 ID 与 schema 校验；失败修复只针对真实校验错误。模型产出的别称或不存在的 ID 不得变成用户需确认的新字段。
5. 每次调用记录召回覆盖、计划修复次数、状态分类以及分阶段耗时，才能分清“没召回”“没理解”“执行器缺能力”“传输失败”。

## 稳定性观察

开始时 U01/U05 并发首轮都在 MCP 连接阶段报 `context deadline exceeded`，工具耗时约 120 秒，客户端旧读取期限也在约 127 秒到期。保存了持久化错误答案，随后重启本地 app 并从单请求预热，U01 恢复（52.31 秒），U05 恢复为合约澄清；后续又执行不同会话并发。只能确认“首轮连接失败，重启后恢复”，不能据此确认是代理、字段模型或并发锁的问题。

下一步应分别记录 Connect/Initialize/ListTools/CallTool/字段模型/查询/最终回答的耗时与取消原因；在初始化、断连、停止后重连、服务更新、并发请求下验证连接状态和超时清理。不能靠把总超时拉长解决。

## 升级顺序与验收门槛

**第一批先阻止错误成功。** 任务覆盖校验；状态分离；单日 bounds 规范化；禁止无工具文件事实与新增数字/单位。U11、U13–16、U44–48 必须有正确完整答案，或者明确、准确的暂不支持说明，绝不能返回不等价的数值或要求用户提供可查到的字段。

**第二批恢复自然追问与别称。** 程序维护上下文槽位；新指标继承已确定维度；候选加入时效/单位/质量；混合召回与字段分类。U03→U04、U08→U09→U10、U41→U42→U43 不应重复澄清已确定内容。真实歧义仍保留。

**第三批扩展分析执行器与展示。** 支持窗口、筛选、Top N、条件计数、跨日多输出、同日对齐、相关性、回撤和图表。库存/累计量的流量语义、零缓存、缺值政策进入结果证据。预测必须区分最后数据日期与预测日期并明确方法；因果解释只能说证据支持到哪一步。

每批在本地 Docker 验收后再进入部署。把本轮真实问题变成固定回归，同时另设未参与调提示词的改写与多轮问题，避免只修本轮句子。字段、数值、日期、出处、范围/筛选、任务完成度、澄清必要性分别评分；不能把工具完成率作为通过率。

## 服务器新案例：首次问复合极值失败（12:29）

用户原话：**“郑棉期货最高价和最低价差值多少？分别是哪天？”**。本节是额外诊断，不改变上面 52 个本地案例的统计。

只读登录服务器核验：当前 release 为 `production-96ff32303151a06ea9d6d7d98acfb34596ee8a7b-38023032397-1`；app 与 structured-data 都运行该版本且健康，字段服务为 `semantic-fields-v22.2-compound-statistics`。本次 Agent 为“表格数据分析（结构化）”，外层回答模型是 `qwen3.8-flash`，字段模型是 `qwen-max`。本地批测外层模型为 `qwen-max`，两者测试条件不应混同。

从持久化消息读取到 2026-10-10 12:29:59 开始的真实请求，全轮耗时 84.712 秒，共 12 次工具调用。首次提问前没有该会话的已确认字段。

## 修复与验收（本地 Docker，deepseek-v4.1-flash）

原先字段模型 qwen-max 在实测中返回 Arrearage。按用户指示先验证 deepseek-v4-flash-0731，随后切换为 **deepseek-v4.1-flash**。最终回放同时记录聊天请求 model_id 和字段模型名称、服务地址；实际字段模型为 deepseek-v4.1-flash（Dashscope compatible-mode）。字段调用显式关闭思考是本地配置的可选项，代码没有按模型名称强制判断。生产模型配置未更改，不能用本地成功推断原生产模型的欠费状态已经解除。

### 实际改动

- 结构化 Agent 由程序直接执行已授权的 resolve/confirm 协议。原问题、文件身份、真实已确认字段与待确认状态分开保存；不可重试的错误立即结束，外层模型不能绕过错误自行挑列、只取最大值或生成未经核实的数值。普通聊天 Agent 保持原路径。
- 字段检索跨完整目录检索别称、实体维度和指标；上轮工作表仅作上下文。补充检索与来源复核识别旧复制列，模型声明同义来源后再按覆盖范围选取。来源复核增加完整共同日期的数值一致性证据，它只是模型语义判断的辅助证据，不能单靠数值一致就自动认定不同业务指标等价。
- 从人类问题提取明确的月份、年份、最近 N 条、Top N、阈值、排零、均值/求和/计数、双极值及日期要求，由执行器执行。均值、求和、计数、Top N 不接受模型另造的自由计算式。字段歧义保留实际选择，不将遗漏操作属性解释成用户字段不清楚。
- 同一系列的最高和最低仅选择一次。已确认系列可用于后续任务，不重复要求相同选择；未确认候选不能冒充确认。任务变化后确认框使用本题文字，不能沿用上一题的统计问题。
- 最终展示由可核验结果生成，并等待本轮最终状态。卡片与文本共享结果和来源，避免先显示失败、随后借上一轮答案再变为确认框。显示值和日期单元格、原表单位、缺数、公式零缓存等边界。
- 支持完整窗口明细、条件计数、Top N、双极值差、跨日差、月内首尾变化/最大回撤、共同日期 Pearson、单系列折线图。累计量求和解释重复计数；缺失输入不借相邻日期、不补零、不伪造基差；旧历史不能给出有依据的明日预测，价格序列不能证明因果。

## 用户补充案例：两个完整年份与错误的单月合计

用户在会话 `bf48898a-29f3-437b-ba60-6d7e063e24ed` 中询问“2022/23年度中国棉花产量加进口，合计是多少？”，随后补充“两年整年的”，系统重复要求年度起止；再补充“2022年1月到23年12月”，实际只计算 2022 年 1 月，返回 82.79，解释却写两年合计。这是上一轮修复和测试的遗漏：U70 只验证了完整日日期的年度边界，未覆盖自然语言补充与简写年份，不能据此宣称年度交互已经完整正确。

### 根因与改动

1. 原时间规则仅匹配首个 `YYYY年M月`，未解析年月范围的终点；“两年整年的”也没有结合原问题中的年份。新增独立日历范围解析，支持上下文中的两个自然年、简写终点年份、同年省略年份、跨年月份范围，并使较新的补充优先于旧口径。识别不了范围终点时不再静默算第一个月。日历规则不包含商品名称或指定某个品种的统计年度定义。
2. 所有补充都套用“选字段”弹窗，唯一字段也被显示成必选单选框。只有缺少时间/说明且没有字段歧义时，直接在卡片内输入并继续；保留唯一字段绑定，提交后聊天仅展示用户补充。只有真正存在多个字段候选时保留选择对话框。
3. 结果解释可以来自模型，未与真实执行范围绑定。期间统计说明改为使用执行器的真实起止范围；月度来源同时显示请求月份数、实际有效月份数和缺月。通过原表日期每月一条记录、月初/月末或固定日期模式核验月度序列，不依靠工作表名称猜频率。未收录月份与现有记录中的空值分开，不把部分数据小计展示成完整期间总量。
