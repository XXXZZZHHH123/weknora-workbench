# 大知识库研究台加载修复

## 问题与结果

本轮实际知识库已增长到1,126,851条原始记录、377个字段。旧实现每次读取113页、约499.7MB JSON，生成549,730条研究有效观测后超过64MiB内存留存预算，因此立即再次打开也重新构建。隔离真实数据测量首次74.05秒、重复77.76秒。

修复后，首次新版本构建约24.78秒；相同版本复用约96ms；新连接并重新完整验签约604ms；强制连接过期后复用约91ms。后三种情况都没有重新读取事实分页。传输降为55页、约81.04MB。它们是隔离投影测量，不是浏览器整页加载时间；实际页面和部署版本另留运行验收记录。新版本首次仍需准备索引，不能据此宣称首次秒开。

独立参考采用旧转换规则、单次只读游标取原始数据，在临时库中逐项比较全部549,730条数值、日期、稳定观测ID及来源单元格、原始值、公式、日期定位。差异为0，排序摘要相同。参考核查耗时单列，不计入候选延迟。

## 加载方式

1. 每次请求先核验当前账号、工作台和绑定知识库，再获取完整当前原件目录、哈希、已确认工作表和结构化版本。
2. 按知识库所属租户、知识库ID、上下游服务地址、投影格式/表结构和当前版本定位可重建的只读索引。不同工作台可以共享同一知识库版本的事实；个人研究成果仍写入各自的原结果库。
3. 没有索引时，跨进程文件锁将同版本构建合并为一次。等待构建后、发布前重新核验工作台绑定、来源和版本；失败不返回旧版本。
4. 索引从完整验证后的TEMP事实备份产生，保留观测与逐行来源证据。对象白名单阻止把其他临时私人数据打包。SQLite文件与HMAC签名在同一版本锁内发布。
5. 首次读取或文件、签名、密钥变更时验证完整文件摘要与HMAC、表结构及元数据；已验证文件可按文件指纹复用。缓存损坏或篡改后从当前知识库重建。
6. 通过`mode=ro&immutable=1`附加索引、用TEMP视图遮蔽结果库历史事实；SQLite只读模式和authorizer共同禁止事实写入、DDL、ATTACH、危险PRAGMA及直接读取历史事实。研究成果仍可正常提交。

知识库仍是唯一事实来源。磁盘索引是可删除、可重建的计算缓存，不提供事实编辑入口，不接受用户或模型指定缓存路径，不在来源失效时回退旧值；不保存问题或答案。

缓存位于研究服务数据目录的`cache/knowledge-facts`，私有目录/文件权限为0700/0600。元数据保留预算合计16MiB，每个附加连接页缓存8MiB；文件清理目标为每个范围两个版本、总计4GiB。活跃读者/构建不能为满足预算而被删除，所以它是清理目标，不能当作全部进程内存或瞬时磁盘的硬上限。初次构建仍有临时内存及磁盘开销。

## 首次构建优化

- DuckDB先按真实字段分组计数，只排序当前页涉及的字段，减少对全表重复排序和深OFFSET；原件、确认、目录与版本检查均保留。
- facts端点在线程池内直接严格编码JSON，日期使用原ISO形式，Decimal沿用原编码规则，拒绝非有限值和未知类型，避免FastAPI重复递归扫描响应。
- 内部可选`research-rows-v1`使用固定八列数组，不重复传输每行已在真实字段目录中明确列出的三个来源ID。客户端按真实canonical字段ID恢复绑定并继续校验；默认接口及其版本语义保持兼容。
- 紧凑协议只传递原研究逻辑已经使用的有效、有日期观测。原始记录计数和200万条上限仍基于所有已确认原始行；NaN/Infinity即使位于无日期或无效状态行也整体拒绝，不借过滤隐藏异常。
- 快照级固定字段只编码一次；日期转换做有界复用，稳定观测ID与证据编码不变。

## 验证与范围

先记录原事实与目录相关52项基线。跨工作台复用、重连和过期三个行为在旧实现上明确失败，修复后通过；补充并发单构建及等锁期间绑定改变的拒绝检查。安全回归覆盖缓存篡改/损坏、跨库/端点隔离、密钥轮换、权限撤销和研究成果提交。

独立变体分别禁用签名验证、固定旧版本，均被真实数值/更新断言捕获；独立四进程构建与GC压力检查通过。紧凑协议还验证默认响应逐字节兼容、跨数据集分页、零值、缺失值、原始计数、非有限值与非法来源绑定。最终全套结果以运行验收记录为准，各批目标测试有重叠，不累加为唯一数量。
